Codebase Context

Grounded against origin/main (release 0.18.0). The team lives in agents/fixer.md, agents/verifier.md, workflows/fix-queue.js, the writing-dispatch-prompts skill and its references, and ADR 0002.

  • Roles today. The lead holds the claim (status:in-progress), orchestrates, runs the adversary review, pushes and opens the PR. The fixer implements through ce-work and commits locally. The verifier runs ce-code-review plus a nine-point checklist (identity, toolchain evidence, fail-before/pass-after, mutation, guard code, acceptance criteria, scope fence, repo verification) and returns VERIFIED / REWORK / ESCALATE.
  • Model and cost. Both profiles declare model: inherit, so neither role is tuned. fix-queue.js enforces one flat minBudgetPerFix of 150k tokens per round. An issue can cost up to three fixer and verifier runs: the first pass plus two rework rounds. Chips launch with an empty MCP roster (measured 172 → 0 servers).
  • Known failures. In #96, verifiers returned CLEARED without running ce-code-review. Under #116, workflow agents have no Agent tool, so every workflow review runs degraded, and a malformed field burns a rework round. #113: needsReverify dead-ends. #114 and #115: claims land before filters, and a crash leaves orphaned claims. #112: unpredicted same-file collisions. #109: the verified-tree recipe swallows failures. #127: enforce the verdict's first line.
  • After CLEARED. fix-queue stops at VERIFIED and returns a "next: adversary review, then push and open the PR" note. Auto-merge runs on green CI, and GitHub closes the issue on the Closes keyword (about 41 seconds after merge for #90). Nothing explicit releases status:in-progress, and no step checks the behavior once the fix is on main.
  • External signal (moderate; search snippets). An agent declaring done too early is a named failure pattern. LLM judges prefer output from their own model family. Graders have measurable false-positive and false-negative rates, about 31% of SWE-bench "passes" rest on weak tests, and Aider separates the planning model from the editing model. Merge queues (Zuul, GitHub) re-test the combined state. No published evidence says which model tier suits which role in a fixer/verifier team.
  • Strategy boundary. docs/strategy/compounding-automation.md prefers extending existing homes over adding plugins.

How 2, 4 and 1 fit together. The acceptance check the PM-style owner writes at intake (4) is the same artifact the mechanical gate runs as fail-before/pass-after (1). The closer replays it where the merged state differs from the verified one (2). One executable definition of done runs from triage to closure, so "closed" means the behavior is fixed, not only that a PR merged.

1. Mechanical gate: code checks, the model judges

Description
Move every deterministic verifier check into a tested script step in fix-queue.js that runs before any verifier agent is spawned. That covers identity, tree binding, 40-hex and field validation, --no-renames scope-fence containment, the fail-before/pass-after test run, and the repo verification command. Have the workflow compute the facts it can read from git (SHA, base, tree, changed files) instead of trusting the fixer's copy, so the fixer writes only what a machine cannot know. A mechanical failure goes back to the fixer as an exact error and does not consume a rework round. The verifier agent then receives the gate's results and spends its tokens on judgment only: correctness review, mutation design, guard-code bypass hunting, and acceptance-criteria fit. This also enforces #127's rule in code: a VERIFIED without a review artifact is rejected.
Basis
  • direct: agents/verifier.md:48, "Identity. HEAD equals the submitted SHA. git merge-base <sha> origin/main equals the submitted base." Also :52, which says to run the changed tests in a detached worktree at base. These are shell recipes an LLM re-executes, and in #96 it skipped them.
  • direct: #116, where the fixer's verified_tree was not 40 hex characters, so the field check returned REWORK (round 1 of 2). The workflow already owns missingFields() (fix-queue.js:381-390).
  • direct: #109, "Recipe swallows failures (no cd, missing exit guard, no prefix)".
Rationale
About half of the nine checks are mechanical. In code they run exactly the same way every time, cost close to zero tokens, and cannot be skipped. That is the structural fix for #96, and it ends rework rounds spent on typos. It also makes model tiering for the verifier (idea 5) a question you can measure, because what remains is pure judgment.
Downsides
The fail-before/pass-after and mutation runs are heavier than a lint, and the gate must handle many repos' test commands. Capturing the tree when ce-work returns still needs a fixer-side trigger. Moving trust from prose to code means this script needs its own test scenarios, building on the existing 35. The cheaper-verifier claim is a hypothesis: the remaining judgment is the hardest part, so measure it before relying on it.

2. A closer role that owns everything after CLEARED

Description
Add an integrator/closer as a new profile in agents/ or a follow-on workflow step, not a new plugin. It takes readyToOpen in merge order after the adversary has CLEARED, pushes, opens the PR with the closing keyword from the template, and watches CI. When the first item in a lane lands, it rebases the next one and hands it to delta re-verification (idea 6). After each merge it keeps a per-issue list of closure conditions: PR merged, issue state read back as CLOSED/COMPLETED, status:in-progress removed, and a closure comment linking the PR and the verdict. In two cases where the merged state can differ from what was verified, it also re-runs the acceptance check on main before signing off: a lane item that was rebased after verification, and an acceptance criterion that CI does not run. If the check fails, it reopens the issue with the failing output and moves it back to ready-for-agent.
Basis
  • direct: fix-queue.js:503, next: 'adversary review, then push and open the PR with Closes #' + r.number. The workflow returns a report, and every step after it is the lead's manual work.
  • direct: ADR 0002 and the shipping dossier. Claim release is "the closing PR, or the lead", and no explicit call that drops the label was found.
  • direct: #90 closed 41 seconds after the merge, and nothing in the workflow or CI did a manual close step. Closure follows the keyword, not the behavior.
  • external: Zuul and GitHub merge queue test the combined state before landing. Paperclip's liveness model treats a merged PR as only one kind of done.
Rationale
This is the integrator the request names, given a concrete contract. Making a bug count as closed is the one step with no owner today. Turning closure into a list of conditions with evidence attached replaces "closed because a keyword matched" with "closed because each condition was checked". The closer's reopen rate becomes the best long-run signal for tuning the fixer and verifier (idea 5).
Downsides
It adds a role that needs push rights, which is outward-facing and changes ADR 0002's rule that the lead owns PRs, so it warrants an ADR. Replaying on main adds little when the fix's test already runs in CI on the merge commit. Limit the replay to rebased items and criteria CI doesn't cover, or it becomes ceremony. It also runs into how the lead reasons about sibling sessions under the multi-session coordination protocol.

3. Host the review in the workflow; DEGRADED is not VERIFIED

Description
Workflow agents have no Agent tool, so ce-code-review inside the verifier can never dispatch its reviewers. Move the review up a level: the workflow runs the reviewer personas as parallel agent() steps, each of which can get its own tier, and writes a review file (depth, findings, degraded flag) that the verifier reads and cannot fabricate. Alongside it, make a degraded review a separate outcome. Each kind of change gets a short list of which degradations it can tolerate, with a compensating step. For example, guard code is never cleared on a degraded review, and docs may be, with the lead reading the diff. A VERIFIED that the list doesn't allow becomes DEGRADED and never enters readyToOpen.
Basis
  • direct: #116, "Agents dispatched by agent() in workflow have no Agent tool → ce-code-review cannot dispatch reviewer subagents … every VERIFIED rests on shallower review than interactive verifier gets". The issue lists workflow-run reviewer passes as option 1.
  • direct: the fix-queue.js report note, "Check coverage for a degraded review before trusting a VERIFIED". The rule is advisory text, and coverage is a free-text field (fix-queue.js:198).
  • external: the FAA Minimum Equipment List: an aircraft can fly with an item inoperative only where the list names the item and a procedure, and otherwise it is grounded.
Rationale
The workflow is the main path, so today the degraded review is the normal case, not the exception. Deciding once, per kind of change, which degradations are acceptable replaces a judgment that whoever reads the report currently makes case by case. It also gives reviewer tiering somewhere to live.
Downsides
It overlaps #116 and #127. The new part is choosing the structural option and adding the DEGRADED outcome, so fold it into those issues rather than opening a parallel track. Running reviewers as workflow steps moves the cost from inside one agent into the workflow budget. It probably raises the cost of each verification while fixing quality, which is exactly why idea 5's measurement matters.
4Intake and admissionConfidence 65%Complexity Medium–High

4. Acceptance owner at intake: the executable brief

Description
This is the product-manager-like role, placed where it has the most effect: before any fixer starts. When issue-triage moves an issue to ready-for-agent, an acceptance owner adds structured fields to the AGENT-BRIEF. They are: acceptance criteria written as commands or test names with expected results (ideally a failing test that fails on main for the stated reason), predicted files, scope fence, and lane hints. Admission validates and uses these fields instead of re-deriving files, scope_fence and ground_truth from the issue text on every run. The fixer's job becomes "make this pass without editing it". The gate (idea 1) and the closer (idea 2) check against the same artifact. For prose-only fixes (much of this repo is skill text), the brief carries a written check list as an explicit fallback.
Basis
  • direct: skills/issue-triage/reference/AGENT-BRIEF.md:1-3, "the authoritative specification that an AFK agent will work from … the agent brief is the contract". Today it is prose with no executable part.
  • direct: fix-queue.js ADMIT_SCHEMA, "ground_truth: what you verified beyond the issue body, dated". Admission re-checks every issue in prose on every run.
  • external: SWE-bench+: about 31% of "passing" patches pass because of weak tests. When the solver writes the test that proves its own fix, it is both setting the bar and clearing it.
Rationale
It separates "what done means" from "who does the work", which is what a PM or acceptance owner is for. Triage already runs once per issue, so the contract is written once instead of re-derived by five later steps. This hand-off sets the quality ceiling for everything after it.
Downsides
The verifier's caveat is real: many issues in this plugin are documentation or skill prose with no natural command to run, so the fallback will be used often and needs its own rules. Writing a failing test at triage costs tokens per issue, including issues that never get fixed. It reaches into issue-triage, a sibling skill, so the composability conventions in CLAUDE.md apply.

5. Measure, then tier: a fix ledger and per-role model args

Description
Have fix-queue write one structured record per issue: claim time, predicted files, and for each round the tokens, model, review depth and verdict, then merge SHA and any later reopen. Replace model: inherit with workflow args (fixerModel, verifierModel, admissionModel, reviewerModel). Start with a hypothesis, not a policy: admission and field work on the cheapest tier, and the verifier on a different tier or family from the fixer, for independence. Let the ledger promote or demote a role's tier when its rework or reopen rate moves. A step-up ladder (a stronger fixer model on the last rework round before escalating to the lead) is one candidate the ledger can test. The ledger also doubles as a claim journal that a crashed run can recover from (see idea 7).
Basis
  • direct: agents/fixer.md:4 and agents/verifier.md:4, model: inherit. fix-queue.js:22-23, one minBudgetPerFix default of 150000 applied to every item and role.
  • external: Aider's architect/editor split (a strong model plans, a cheap one edits, about 14x cheaper). Anthropic's research system uses a lead plus cheaper subagents. LLM judges prefer output from their own model family. Web research found no published evidence on which model tier fits which role, so this team has to measure its own.
Rationale
Every model-choice argument for this team is currently opinion. A ledger is cheap, because the workflow already tracks its budget, and it turns tiering into a fitness function. It also makes the verifier's independence real: today the model that wrote a fix reviews it.
Downsides
Not yet verified: whether workflow agent() calls accept a per-call model (current call sites pass only agentType, label, phase and schema). If they don't, tiering has to go through per-tier agent profiles. A ledger only becomes useful after several batches, so the first tiering choices are still guesses. A cheaper verifier may raise the rate of wrong CLEARED verdicts, so tier the verifier last.
6Rework and recovery loopConfidence 70%Complexity Small–Medium

6. Delta re-verification by patch identity

Description
Add a reverify mode to fix-queue that takes a branch that is already claimed and verified and skips admission. After rebasing a later lane item onto the landed fix, compare git patch-id of the rebased commit with the verified one. If they are identical, the verdict carries forward: run only the mechanical gate (idea 1) on the new SHA and re-bind the tree. If they differ, send the verifier only the difference between the two diffs. The closer (idea 2) triggers this once each lane predecessor merges.
Basis
  • direct: #113, "Remedy fails: issue still carries status:in-progress (skipped on re-run); worktree/branch exist (fresh branch cut instead)". #113 also names "add reverify mode to fix-queue" as an option.
  • direct: fix-queue.js:99-105, "Rebasing onto the earlier fix makes a new, unverified SHA, so it is reported under needsReverify".
  • external: git patch-id is git's standard way to fingerprint a change independently of its base, and git cherry uses it.
Rationale
Lane serialization is the workflow's answer to same-file collisions, but every item after the first in a lane dead-ends, so its cost is a manual loop. Making re-verification nearly free lets the workflow serialize aggressively, and it is the smallest change on this list that removes a real dead end.
Downsides
It overlaps #113, so this is a design choice for that issue rather than a new track. A matching patch-id doesn't prove behavior is the same when the base's behavior changed underneath, which is why the gate re-runs the tests. It does not solve collisions on files nobody predicted (#112).

7. Claims as leases; admission as a pure read

Description
Change the order of admission. The admission agent reads and checks candidates but writes nothing to GitHub. The workflow then applies scopeFence, maxFixes and duplicate filtering in code, and only the issues that survive get status:in-progress, plus a claim comment stamped with the run ID and time. A sweeper releases leases whose run ID has no live run, so a crashed run leaves no orphaned claims and other sessions can tell a live claim from a stale one.
Basis
  • direct: #114, "Admission agent never sees scopeFence keys, so it claims status:in-progress and creates worktrees for issues filtered out later. Wastes maxFixes slots and leaves orphaned claim labels."
  • direct: #115 N5, "If admission agent throws … run dies with no report after claim labels already applied."
  • direct: the admission prompt (fix-queue.js:219) runs gh issue edit --add-label from inside the LLM.
Rationale
It fixes #114 and #115 N5 together by removing the cause rather than patching each. It also makes the multi-session claim protocol crash-safe, which matters more as more fixer batches run in parallel.
Downsides
It overlaps #114 and #115, and the new part is moving the claim into code. A lease sweeper needs a reliable signal that a run is still alive, which a label alone can't carry. That ties it to idea 5's ledger.

# Vocabulary discovery

This skill hardcodes **no label names**. It reads them at triage time. That is deliberate:
every copy of the triage vocabulary made in this org has since gone stale (see
[`UPSTREAM.md`](./UPSTREAM.md)). A skill with no vocabulary has nothing to rot.

## Two sources, two scopes

They are not interchangeable, and neither is authoritative over the other's axis.

| Source | Scope | Governs | Authority |
|---|---|---|---|
| `<repo>/docs/agents/triage-labels.md` | Per-repo | state roles, category roles, `priority:*`, `area:*`, local extensions | The repo |
| `devops-excellence/templates/role-labels.json` | Org-wide | the legal `handling:route:*` values | GlassFrog, via SAE-009 |

This split is why route inference runs in **every** IP repo, including the ones whose
`triage-labels.md` never mentions routing. Those docs are not wrong about routing — routing
was never theirs to define. SAE-009 put that authority in GlassFrog.

## Reading the repo vocabulary

```bash
gh api "repos/$OWNER/$REPO/contents/docs/agents/triage-labels.md" \
  --jq '.content' | base64 -d
```

Parse out:

- **state roles** — exactly one per issue
- **category roles** — exactly one per issue
- **enrichment axes** — `priority:*`, `area:*`, and any repo-local axis; these *add* signal
  and never replace a state
- **retired labels** — a "do not use" list, if present. Never apply one, and flag any issue
  already carrying one.
- **lock labels** — e.g. praxis `status:in-progress`. A lock is **not** a state. Never set
  or clear one during triage; it belongs to the dispatch claim protocol.

### Known divergence between repos

Do not assume the vocabulary you read last time. Measured 2026-08-02:

- **praxis** — 6 states (adds `deferred`), 2 categories, plus `priority:*`, `area:*`,
  `handling:route:*`, and the `status:in-progress` lock. Its `deferred` means *"parked on an
  external/dependency trigger that hasn't fired yet; not awaiting reporter info."*
- **skills** — also 6 states, but glosses `deferred` differently: *"valid but blocked on
  graduation conditions."*
- **devops-excellence** — 5 states, no routing axis, adds Conventional-Commit type labels.
- **Seven other repos** — byte-identical 5-state boilerplate with no local adaptation.

The `deferred` gloss differing between praxis and skills is a live divergence. Read the
repo's own wording; do not port one repo's meaning to another.

### When the repo has no `triage-labels.md`

Four repos have none (including this one). Fall back to the canonical roles —
`bug` / `enhancement`, and `needs-triage` / `needs-info` / `ready-for-agent` /
`ready-for-human` / `deferred` / `wontfix` — and **say so in the triage comment**. A silent
fallback is how a repo ends up with a vocabulary nobody chose.

Before applying, confirm what actually exists:

```bash
gh label list --repo "$OWNER/$REPO" --limit 200 --json name --jq '.[].name'
```

## Reading the route vocabulary

```bash
gh api repos/Integral-Productivity/devops-excellence/contents/templates/role-labels.json \
  --jq '.content' | base64 -d
```

Generated by `scripts/generate-role-labels.ts` from the GlassFrog org tree (ADR-074).
137 deduped roles, 71 structural. Entry shape:

```json
{
  "name": "handling:route:accounting",
  "color": "0052cc",
  "description": "Accounting · finance · gf:role_d6b8bef4ed2c4a1594ea0b888a758b27",
  "roleId": "role_d6b8bef4ed2c4a1594ea0b888a758b27",
  "roleName": "Accounting",
  "circleName": "Finance",
  "structural": false
}
```

Three properties that matter downstream:

- **`roleId` is a join key.** This manifest carries names only — no purposes, no
  accountabilities. Inference needs those, and they live in a **sibling manifest** in the same
  directory:

  ```bash
  gh api repos/Integral-Productivity/devops-excellence/contents/templates/role-context.json \
    --jq '.content' | base64 -d
  ```

  `role-context.json` holds 137 entries keyed by `roleId`, each with `purpose`,
  `accountabilities`, and `domains`. Generated by the same script, regenerated by the same
  workflow. Join the two on `roleId` — no GlassFrog session required. See
  [`route-inference.md`](./route-inference.md).
- **`structural: true`** roles (`Secretary`, `Facilitator`, `Circle Lead`, `Circle Rep`)
  exist once per circle, so their label name carries the circle:
  `handling:route:<circle>:<role>`. Everything else is named alone — GitHub caps label names
  at 50 characters and `handling:route:` already spends 15.
- **The `description` carries the `gf:` key.** Preserve it exactly when creating a label. It
  is what lets a GlassFrog rename follow the label instead of orphaning it, and it is what
  devops-excellence's `role-label-vocabulary` fitness check reads.

**Never hand-author a route value.** If a role you want is not in the manifest, the manifest
is the thing to fix — regenerate it upstream rather than inventing a label here.

## Lazy label provisioning

All 137 route values are legal everywhere, but a label is created in a repo only when an
issue actually needs it. Eager provisioning would mint roughly 13,000 labels across 92 active
repos. This is the ADR-074 / ADR-039 self-create precedent.

Create with the manifest's exact three fields:

```bash
gh label create "$NAME" --repo "$OWNER/$REPO" \
  --color "$COLOR" --description "$DESCRIPTION"
```

`needs-triage-decision` needs the same treatment. Measured 2026-08-02 it exists **only in
praxis**, where it carries zero issues — an untested escape hatch. If the confidence gate
escalates in any other repo, create it first:

```bash
gh label create needs-triage-decision --repo "$OWNER/$REPO" \
  --color "d876e3" \
  --description "Ambiguous issue requiring human triage. Posted by the Triager agent."
```

Roles are never deleted, only deprecated — so a label that no longer resolves is a signal to
reconcile, not to delete. `devops-excellence/scripts/reconcile-role-labels.ts` handles
rename/restamp/adopt/deprecate and **never creates and never deletes**; leave that job to it.
